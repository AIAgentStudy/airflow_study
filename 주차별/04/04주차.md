### 주차 맞춤 시나리오

- 시나리오 A (Variable 누락): `Variable.get("없는키")`로 KeyError 발생 확인
- 시나리오 B (Connection 오타): 잘못된 conn_id 사용으로 연결 실패 재현
- 시나리오 C (기본값 복구): default_var/fallback conn으로 부분 복구 후 재실행

### 추가 예외 케이스(운영형)

- 시나리오 D (Variable 빈 값): 키는 존재하지만 `""` 또는 공백값이라 로직 실패
- 시나리오 E (conn_id 빈 값): Trigger conf에 `conn_id`를 빈 문자열로 넣어 설정 검증 실패
- 시나리오 F (지원하지 않는 scenario): 오타/잘못된 scenario 입력 시 즉시 실패
- 시나리오 G (Connection host 누락): Connection은 존재하지만 host 값 미입력 상태 검증

### Trigger 예시(JSON conf)

- 정상 실행: `{"scenario":"happy_path","conn_id":"postgres_default"}`
- Variable 누락: `{"scenario":"missing_variable"}`
- Connection 오타: `{"scenario":"bad_connection"}`
- 기본값 복구: `{"scenario":"fallback_recovery"}`
- 빈 Variable 검증: `{"scenario":"empty_variable"}`
- 빈 conn_id 검증: `{"scenario":"empty_conn_id","conn_id":""}`
- host 누락 검증: `{"scenario":"conn_without_host","conn_id":"postgres_no_host"}`
- 잘못된 scenario 검증: `{"scenario":"typo_case"}`

### 이번 주 추가 학습 포인트

- `AirflowFailException`을 써서 실패 이유를 명시적으로 남기는 방법
- `dag_run.conf` 입력 검증(허용값 리스트, 빈 값 방지)
- 실패를 "빨리/명확하게" 내는 fail-fast 패턴의 장점
- 재시도(`retries`)와 설정 오류의 관계: 재시도로 해결되지 않는 오류 구분
